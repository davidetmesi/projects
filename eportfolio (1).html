    Unit 01

    Introduction and Recap of Object-Oriented Programming (OOP)

    Unit 1 re-establishes the core vocabulary of object-oriented programming before the course builds on top of it. It revisits classes and objects as the basic unit of design, and walks back through the four pillars: encapsulation, abstraction, inheritance, and polymorphism — this time with an eye on why each one exists, not just how to write the syntax.

    A class is treated less as "a template for objects" and more as a promise: a bundle of state and behaviour that guarantees certain things stay true no matter who is using it. Objects are the runtime instances of that promise, each with its own state but sharing the same contract. The unit uses this framing to explain why encapsulation isn't about hiding data for its own sake, but about protecting the invariants a class depends on to behave correctly.

    The recap matters because every later unit — SOLID, patterns, architecture — is really a more disciplined way of applying these same four ideas at a larger scale.

    Key concepts

    Encapsulation

    Bundling state and behaviour together, and restricting direct access to internal state through a controlled interface.

    Abstraction

    Exposing only what a consumer needs to know, and hiding the implementation details behind it.

    Inheritance

    Sharing structure and behaviour through an "is-a" relationship — powerful, but easy to overextend.

    Polymorphism

    Letting different classes respond to the same message in ways appropriate to each, resolved at runtime.

    Example in practice

    A small illustration used in the unit: a Shape base type with Circle and Rectangle subtypes, each implementing its own area() method. Calling code never checks "what kind of shape is this" — it simply calls area() and lets polymorphism route the call correctly.

    abstract class Shape {
  abstract area(): number;
}

class Circle extends Shape {
  constructor(private radius: number) { super(); }
  area() { return Math.PI * this.radius ** 2; }
}

class Rectangle extends Shape {
  constructor(private w: number, private h: number) { super(); }
  area() { return this.w * this.h; }
}

// calling code doesn't need to know which subtype it has
shapes.forEach(s => total += s.area());

    Topics covered

    • Classes, objects, and the object-oriented mental modelA class defines the blueprint — the fields and methods any instance will have — while an object is a concrete instance built from that blueprint at runtime. Thinking in objects means modelling a problem as a set of collaborating things, each responsible for its own state and behaviour, rather than as a single script that pushes data through a sequence of functions. That shift in mental model, more than any particular syntax, is what the rest of the course builds on.
    • Encapsulation and access controlEncapsulation means keeping an object's internal state private and only exposing a deliberate, controlled interface for interacting with it. Access modifiers like private and protected aren't there to be bureaucratic — they draw a line between the parts of a class other code is allowed to depend on and the parts that are free to change without breaking anything. A well-encapsulated class can have its internals rewritten completely as long as its public contract stays the same.
    • Abstraction and designing minimal public interfacesAbstraction is about deciding what a caller actually needs to know to use a class, and hiding everything else behind that. A well-designed public interface reads like a short, honest description of what an object can do, without leaking details about how it does it. Keeping that surface small also keeps the class easier to change later, since fewer external callers are coupled to its internals.
    • Inheritance vs. composition, and when each is appropriateInheritance models a strict "is-a" relationship and shares both structure and behaviour down a class hierarchy, which is powerful but can become rigid once a hierarchy grows past two or three levels. Composition instead builds an object out of smaller collaborating parts, favouring "has-a" relationships that can be swapped or recombined more freely. The unit's guidance is to reach for composition first, and treat inheritance as a deliberate choice rather than a default.
    • Polymorphism and dynamic dispatchPolymorphism lets different classes respond to the same method call in ways appropriate to each of them, with the correct implementation resolved at runtime based on the object's actual type. This is what lets calling code stay simple — it can call one method name across many different subtypes without ever needing to check which one it's talking to. Dynamic dispatch is the underlying mechanism that makes that resolution happen automatically.
    • Constructors, invariants, and valid object stateAn invariant is a condition that should always hold true for an object — for example, a bank account balance never going negative — and a constructor's core job is to make sure an object can never be created in a state that breaks one. Once that guarantee is in place at construction time, every method on the class can assume it's working with valid data, which simplifies the rest of the class considerably.
    • Where procedural habits leak into OO codeEven in an object-oriented language, it's easy to write code that's procedural in spirit — static utility classes that hold no state, "anemic" data classes with no real behaviour, or long methods that push data through a sequence of steps rather than letting objects act on their own behalf. Spotting these habits early is the first step toward a design that actually uses what OOP offers.
    encapsulation inheritance polymorphism abstraction class design

    Reflection

    Coming back to these fundamentals with a few more years of practice made the trade-offs clearer — inheritance in particular reads differently once you've felt the cost of a rigid class hierarchy. The unit's framing of encapsulation as "protecting invariants" rather than "hiding fields" was a small shift in language that changed how I read my own older code — a lot of bugs I've hit before were really invariants that were never enforced in the first place.

    Unit 02

    SOLID Principles of Object-Oriented Design

    Unit 2 introduces the five SOLID principles as a shared vocabulary for talking about design quality: Single Responsibility, Open/Closed, Liskov Substitution, Interface Segregation, and Dependency Inversion. Each principle is examined through small before-and-after refactors that show a design violating it, and then correcting it.

    The unit is careful to frame SOLID as a diagnostic tool rather than a checklist to apply blindly. Each principle is paired with a "smell" that signals its violation — a class with an unrelated second job, a subclass that throws on a method its parent supports, an interface that forces implementers to stub out methods they don't need. Learning to recognise the smell turns out to matter more than memorising the definition.

    SOLID is less a set of rules than a set of smells to watch for — each principle names a specific way a class can become hard to change.

    Key concepts

    SRP

    A class should have one reason to change — one axis of responsibility, not several bundled together.

    OCP

    New behaviour should be added by extending a design, not by editing code that already works.

    LSP

    A subtype must be usable anywhere its base type is expected, without surprising callers.

    ISP & DIP

    Prefer small, focused interfaces, and depend on abstractions rather than concrete classes.

    Example in practice

    An early exercise takes an InvoicePrinter class that formats an invoice, saves it to disk, and emails it — three responsibilities in one class. Splitting it into InvoiceFormatter, InvoiceStorage, and InvoiceMailer makes each piece independently testable and replaceable.

    // before — one class, three reasons to change
class InvoicePrinter {
  format(invoice) { /* ... */ }
  saveToDisk(invoice) { /* ... */ }
  emailTo(invoice, address) { /* ... */ }
}

// after — one responsibility per class
class InvoiceFormatter { format(invoice) { /* ... */ } }
class InvoiceStorage   { save(invoice)   { /* ... */ } }
class InvoiceMailer    { send(invoice, to) { /* ... */ } }

    Topics covered

    • Single Responsibility Principle — one reason to changeA class should have exactly one reason to change, meaning it should own exactly one axis of responsibility rather than several unrelated ones bundled together. When a class mixes concerns — say, business logic and file I/O — a change to one concern risks breaking the other, and the class becomes harder to test in isolation. Splitting responsibilities apart, even when it means more classes, tends to make each piece both simpler and more stable.
    • Open/Closed Principle — open for extension, closed for modificationA well-designed module should be open to having new behaviour added, but closed to having its existing, working code edited to do it. In practice this usually means designing around interfaces or abstract base classes, so that a new case can be handled by adding a new implementation rather than reopening and risking code that already passes its tests.
    • Liskov Substitution Principle — subtypes must honour base-type contractsAny subtype should be usable wherever its base type is expected, without the caller noticing a difference in behaviour it wasn't told to expect. Violations often look reasonable in isolation — a subclass that throws where the parent wouldn't, or ignores an argument the parent respects — but they break the assumption that lets polymorphism be trusted in the first place.
    • Interface Segregation — many small interfaces over one large oneNo class should be forced to depend on methods it doesn't actually use. A single bloated interface tends to accumulate unrelated methods over time, forcing every implementer to stub out things that don't apply to it. Splitting it into several smaller, more focused interfaces lets each implementer depend only on what it genuinely needs.
    • Dependency Inversion — depending on abstractions, not concretionsHigh-level modules that contain business logic shouldn't depend directly on low-level modules like a specific database driver or file system; both should depend on a shared abstraction instead. This inversion is what allows the low-level details to be swapped out — for testing, or for a future migration — without having to touch the business logic that sits above them.
    • Recognising SOLID violations as code smellsEach SOLID principle pairs with a concrete, recognisable smell: an unrelated second responsibility, a subclass that throws where its parent wouldn't, an interface implementers only partially support, a class that constructs its own dependencies directly. Learning to spot the smell in the wild turns out to matter more day-to-day than being able to recite the principle's definition from memory.
    • Trade-offs — SOLID applied too early can over-engineer a simple designSOLID is a diagnostic tool for managing change, not a checklist to apply uniformly to every class. Introducing interfaces, abstraction layers, and injected dependencies for a piece of code that's genuinely simple and unlikely to change adds indirection without buying anything back — the unit is explicit that judgement about where change is actually likely matters more than mechanically applying every principle everywhere.
    SOLID design principles Liskov substitution dependency inversion

    Reflection

    Liskov Substitution was the principle I understood least well going in, and the classic rectangle/square example finally made the contract-based framing click: violating LSP isn't about broken syntax, it's about a subtype quietly breaking a promise its base type made to callers. It also reframed a few "clever" subclasses from past projects as, in hindsight, LSP violations waiting to surface.

    Unit 03

    Design Patterns I — Creational Patterns

    Unit 3 opens the Gang of Four catalogue with the creational patterns, which govern how objects are instantiated. The unit covers Singleton, Factory Method, Abstract Factory, Builder, and Prototype, comparing them against plain constructors to show what each one buys you.

    A recurring theme is that constructors are a poor place to put decision logic. The moment "which class do I instantiate" or "how many steps does this object need to be built correctly" becomes non-trivial, a plain new call starts to leak that complexity into every call site. Each creational pattern is a different way of moving that decision somewhere more controllable.

    Creational patterns exist to separate "what gets built" from "how it gets built" — a distinction that pays off the moment construction logic gets complicated.

    Key concepts

    Singleton

    Guarantees a single instance and a global access point — useful sparingly, risky as a default habit.

    Factory Method

    Lets subclasses decide which concrete class to instantiate, behind a common creation method.

    Abstract Factory

    Produces families of related objects that are guaranteed to work together.

    Builder & Prototype

    Builder assembles complex objects step by step; Prototype creates new objects by cloning existing ones.

    Example in practice

    The Builder exercise constructs an HttpRequest object that has several optional parts — headers, query params, a body — without a constructor that takes six optional arguments in a fixed order.

    const request = new RequestBuilder()
  .setUrl("/api/orders")
  .setMethod("POST")
  .addHeader("Content-Type", "application/json")
  .setBody({ item: "widget", qty: 3 })
  .build();

    Topics covered

    • Singleton — and why it's often overusedSingleton guarantees exactly one instance of a class exists and gives the whole program a single, global point of access to it. That global access is exactly what makes it risky to overuse: it introduces hidden global state that's easy to reach for but hard to isolate in tests, since any test touching that class is implicitly sharing state with every other test that touches it too.
    • Factory Method — deferring instantiation to subclassesFactory Method defines a method for creating an object but lets subclasses decide which concrete class actually gets instantiated. This keeps the calling code decoupled from specific concrete classes — it only ever talks to the abstract factory method, while the decision about exactly which subtype to build is delegated further down the hierarchy.
    • Abstract Factory — families of related objectsAbstract Factory produces whole families of related objects that are guaranteed to work together, without the calling code needing to know which concrete family it's using. A classic example is a UI toolkit that can produce a matching set of buttons, checkboxes, and menus for either a light or dark theme, chosen once and applied consistently everywhere.
    • Builder — assembling complex objects step by stepBuilder replaces a constructor with a long, error-prone list of optional arguments with a readable, chainable sequence of steps that assembles a complex object piece by piece. It's particularly useful when an object has many optional parts, since each call to the builder names exactly what it's setting instead of relying on argument position.
    • Prototype — cloning existing instancesPrototype creates new objects by cloning an existing, already-configured instance rather than building one from scratch. This is useful when constructing an object from raw inputs is expensive or complicated, but a similar object already exists that can simply be copied and then lightly adjusted.
    • Constructors as a design smell when logic accumulatesWhen a constructor starts accumulating conditional logic, optional parameters, or multi-step setup, that complexity is a sign that instantiation itself deserves its own dedicated pattern rather than being crammed into the class's constructor. Recognising this early keeps the class's core responsibilities separate from the increasingly complicated question of how to build one correctly.
    • Choosing between patterns based on how instantiation actually variesThe right creational pattern depends on exactly what varies at construction time: if it's which concrete class to build, Factory Method or Abstract Factory fit; if it's the number of optional steps, Builder fits; if it's cheaply copying an existing configuration, Prototype fits. The unit's exercises repeatedly come back to matching the pattern to the specific kind of variability at hand.
    creational patterns singleton factory method builder

    Reflection

    The Builder pattern mapped directly onto a config object I'd been passing around awkwardly in a past project — a good reminder to look for patterns in existing pain points, not just new code. Singleton was also a useful cautionary tale: easy to reach for, but it quietly introduces global state that makes testing harder, which the unit was careful to flag rather than present as a free win.

    Unit 04

    Design Patterns II — Structural Patterns

    Unit 4 moves to structural patterns, which describe how classes and objects are composed into larger structures while keeping those structures flexible. The unit works through Adapter, Decorator, Facade, Composite, Proxy, and Bridge.

    A useful distinction drawn early in the unit: some structural patterns change an interface (Adapter), some add behaviour (Decorator), some hide complexity (Facade), and some control access (Proxy). They can look alike in a class diagram — often just an object wrapping another object of the same interface — so the unit pushes on intent as the real differentiator, not shape.

    Where creational patterns focus on birth, structural patterns focus on shape — how independently designed pieces can still fit together cleanly.

    Key concepts

    Adapter

    Wraps an incompatible interface so it can be used where a different one is expected.

    Decorator

    Wraps an object to layer on extra behaviour, transparently, without touching its class.

    Facade

    Offers one simple entry point in front of a complex subsystem with many moving parts.

    Composite, Proxy, Bridge

    Composite unifies trees of objects; Proxy controls access; Bridge separates abstraction from implementation.

    Example in practice

    The Decorator exercise wraps a plain Coffee object with MilkDecorator and SugarDecorator, each adding cost and description without subclassing Coffee for every combination.

    let order = new Coffee();
order = new MilkDecorator(order);
order = new SugarDecorator(order);

order.cost();        // base + milk + sugar
order.describe();    // "Coffee, milk, sugar"

    Topics covered

    • Adapter — reconciling incompatible interfacesAdapter wraps an existing class so that its interface matches whatever a caller is expecting, without modifying the original class at all. It's especially useful when integrating a third-party library whose interface doesn't line up with the rest of a codebase — the adapter absorbs that mismatch in one place instead of scattering workarounds everywhere the library is used.
    • Decorator — adding behaviour without subclassingDecorator wraps an object to layer additional behaviour on top of it at runtime, transparently, without needing a new subclass for every possible combination of extra behaviour. Multiple decorators can be stacked on the same base object, each adding its own small piece of functionality independently of the others.
    • Facade — a simple front for a complex subsystemFacade provides one clean, simple entry point in front of a subsystem that internally has many moving, interdependent parts. Callers interact only with the facade's simplified methods, while the facade itself handles the coordination of whatever complexity sits behind it, keeping that complexity from leaking out to every caller.
    • Composite — treating individual objects and groups uniformlyComposite lets a caller treat a single object and a whole tree of objects through exactly the same interface — calling one method on a composite node applies it recursively to every child underneath. This is the pattern behind file-system-like structures, where a single file and an entire folder of files can both respond to the same operation.
    • Proxy — controlling access to another objectProxy stands in for a real object and controls access to it, which might mean delaying expensive creation until it's actually needed, checking permissions before forwarding a call, or adding logging around every access. From the caller's point of view, a proxy looks identical to the real object, so the extra control layer is entirely invisible.
    • Bridge — decoupling abstraction from implementationBridge separates an abstraction from its implementation so that the two can vary independently, rather than being locked together in a single inheritance hierarchy. A shape abstraction, for instance, can be paired with different rendering implementations, and either side can change without forcing a change on the other.
    • Telling structurally similar patterns apart by intent, not shapeSeveral structural patterns look almost identical on a class diagram — often just one object wrapping another that shares its interface — so the real way to tell them apart is by asking what problem they're solving: reconciling an interface, adding behaviour, simplifying access, or controlling it. The unit's side-by-side comparisons made that distinction concrete rather than theoretical.
    structural patterns decorator adapter facade

    Reflection

    Decorator and Proxy look similar on a class diagram but solve very different problems — the unit's side-by-side comparison was the clearest way I've seen that distinction taught. It also made me more careful about naming: a class called "Wrapper" tells a reader nothing about which of these six patterns is actually in play.

    Unit 05

    Design Patterns III — Behavioural Patterns

    Unit 5 completes the pattern catalogue with the behavioural patterns, which manage algorithms and the assignment of responsibility between objects. Strategy, Observer, Command, State, Template Method, and Iterator are each worked through with a small scenario.

    Where structural patterns are about shape, behavioural patterns are about responsibility — which object decides what happens next, and how that decision can change without every collaborator needing to know about it. The unit repeatedly returns to one question: if this behaviour needs to change tomorrow, does that require editing one small object, or hunting through several classes for scattered conditionals?

    Behavioural patterns are about conversation — how objects talk to each other without becoming tightly coupled to the way that conversation happens.

    Key concepts

    Strategy

    Swaps interchangeable algorithms behind one interface, chosen at runtime rather than hard-coded.

    Observer

    Lets one-to-many notification happen without the subject knowing concrete details about its listeners.

    Command

    Turns a request into an object, enabling queuing, logging, and undo.

    State, Template Method, Iterator

    State changes behaviour with internal state; Template Method fixes a skeleton with pluggable steps; Iterator gives uniform traversal.

    Example in practice

    The Strategy exercise swaps pricing algorithms for an order total — regular, seasonal-discount, and loyalty-member — without a chain of if/else checks inside the order class itself.

    class Order {
  constructor(private pricing: PricingStrategy) {}
  total(items) { return this.pricing.calculate(items); }
}

order.pricing = new LoyaltyDiscountStrategy();
order.total(cart);  // swapped without touching Order

    Topics covered

    • Strategy — interchangeable algorithms behind a common interfaceStrategy defines a family of interchangeable algorithms behind one shared interface, letting the algorithm in use be swapped at runtime instead of selected through a branching conditional buried inside a class. Each concrete strategy is independently testable, and adding a new one doesn't require touching the code that already exists.
    • Observer — one-to-many notification without tight couplingObserver lets one subject notify many interested listeners when something changes, without the subject needing to know anything concrete about who those listeners are. This is the pattern underneath most event-driven UI code, and the unit pairs it with a caution about memory leaks when listeners are registered but never properly cleaned up.
    • Command — encapsulating a request as an objectCommand turns a request or action into a first-class object with its own data and an execute method, rather than a plain method call. Once a request is an object, it can be queued, logged, passed around, or reversed — capabilities that are difficult to add on top of an ordinary direct method call after the fact.
    • State — behaviour that changes with internal stateState delegates an object's behaviour to a separate state object that's swapped out as the object's internal status changes, replacing a large conditional that checks the current state everywhere behaviour needs to differ. Each state object only needs to know how to behave in its own specific state, keeping the logic for each state cleanly separated.
    • Template Method — fixed skeleton, customisable stepsTemplate Method fixes the overall shape of an algorithm in a base class, while leaving specific steps open for subclasses to fill in. This keeps the overall sequence consistent and enforced in one place, while still allowing meaningful variation at exactly the points where it's needed.
    • Iterator — uniform traversal over different collectionsIterator gives consistent, step-by-step access to elements in a collection without exposing how that collection is actually structured underneath. Calling code can traverse an array, a tree, or a linked list through the exact same interface, without needing to know or care which one it's actually working with.
    • Replacing conditional logic with polymorphic dispatchA long chain of if/else or switch statements checking an object's type or state is often a sign that the responsibility belongs inside the objects themselves rather than in a caller reasoning about them from outside. Behavioural patterns like Strategy and State are, in large part, structured ways of making that replacement.
    behavioural patterns strategy observer command

    Reflection

    Observer felt the most familiar coming in — most event-driven UI code I've written is really an informal version of it — but naming it properly made the trade-offs around memory leaks and listener cleanup much more explicit. Command was the bigger surprise: turning a request into an object feels unnecessary until you need undo, logging, or queuing, at which point it's almost the only clean option.

    Unit 06

    Concurrency and Parallelism in Object-Oriented Design

    Unit 6 shifts from static structure to runtime behaviour under concurrency. It distinguishes concurrency from parallelism, then looks at how shared mutable state inside objects becomes a liability once multiple threads are involved, and what design responses are available.

    Concurrency is framed as "dealing with more than one thing at once," while parallelism is "doing more than one thing at the exact same instant" — a distinction that matters because a program can be concurrent on a single core, but only parallel with multiple ones. The unit then walks through what happens when two threads read-modify-write the same object field without coordination, and the several ways an object's design can prevent that from being possible in the first place.

    Thread safety is a design property, not an afterthought — the unit's central argument is that it has to be designed in at the class level, not patched on later with locks.

    Key concepts

    Race condition

    Two threads read-modify-write shared state without coordination, producing a result that depends on timing.

    Locks & monitors

    Mechanisms that serialise access to a critical section so only one thread modifies shared state at a time.

    Immutability

    An object that can't change after construction has no race conditions to worry about — it's inherently safe to share.

    Thread pools

    Reusing a fixed set of worker threads for many short tasks instead of creating a thread per task.

    Example in practice

    A simple Counter class shows the problem directly: without synchronisation, two threads calling increment() concurrently can both read the same value before either writes it back, silently losing an update.

    // unsafe — read-modify-write is not atomic
class Counter {
  private count = 0;
  increment() { this.count = this.count + 1; }
}

// safer — synchronised access to the critical section
class SafeCounter {
  private count = 0;
  private lock = new Mutex();
  increment() { lock.runExclusive(() => this.count++); }
}

    Topics covered

    • Concurrency vs. parallelism, and where each appliesConcurrency is about structuring a program to deal with more than one task making progress at once, while parallelism is specifically about tasks running at the exact same instant on different cores. A program can be concurrent on a single core through interleaving, but it can only be truly parallel with multiple cores actually available to it — a distinction that shapes which tools and guarantees are relevant.
    • Shared mutable state and race conditionsA race condition happens when two threads read, modify, and write the same piece of shared state without any coordination, so the final result ends up depending on the unpredictable timing of which thread ran first. These bugs are notoriously hard to reproduce, since they may only show up under specific timing conditions that don't always occur.
    • Locks, monitors, and synchronised methodsLocks and monitors are mechanisms for making sure only one thread can execute a critical section of code — the part that touches shared state — at any given time. Synchronised methods apply this automatically at the method level, though the unit stresses that locking has to be scoped carefully to avoid serialising more of the program than necessary.
    • Immutable objects as a concurrency strategyAn object that can never change after it's constructed has no state for two threads to race over, which makes it inherently safe to share across threads without any locking at all. This turns immutability from a stylistic preference into a concrete concurrency strategy — the safest data to share is data that simply can't change.
    • Thread pools and task-based concurrencyRather than spawning a brand-new thread for every task, a thread pool reuses a fixed set of worker threads to process a stream of incoming tasks. This avoids the overhead of constantly creating and destroying threads, and gives a program predictable control over how many tasks are actually running at once.
    • Deadlock, livelock, and how lock ordering prevents themDeadlock happens when two or more threads each hold a lock the other needs and wait on each other forever; livelock is the related case where threads keep responding to each other without ever making real progress. Consistently acquiring locks in the same fixed order across the whole codebase is the standard way to make deadlock structurally impossible rather than merely unlikely.
    concurrency race conditions immutability thread safety

    Reflection

    The push toward immutability as a first line of defence reframed a lot of earlier design choices — an immutable object is, among other things, a concurrency simplification. Working through the deadlock scenario by hand, tracing which thread was waiting on which lock, made "always acquire locks in a consistent order" feel like earned advice rather than a rule to memorise.

    Unit 07

    Secure Coding Practices in Object-Oriented Programming

    Welcome to Unit 7. This week, we shift our focus to secure coding practices, a critical aspect of professional software development. The unit looks at how the same OO principles used for maintainability — encapsulation, least privilege, clear contracts — double as defensive tools once security is the concern.

    The unit's starting point is that a class's public interface is also its attack surface: every method that accepts input from outside the object is a place where an attacker gets a say in what happens next. From there it works through the classes of vulnerability that show up most often in object-oriented systems, and the specific design habit that closes each one — validating at the boundary, never trusting a caller's claim about object state, and failing safely rather than failing open.

    Most vulnerabilities in object-oriented systems trace back to an object trusting input, state, or a collaborator that it shouldn't have — encapsulation is as much a security boundary as a design one.

    Key concepts

    Trust boundary

    Any point where data crosses from an untrusted source into your object graph — the place validation has to happen.

    Least privilege

    Giving a class, method, or user only the access it strictly needs, nothing more.

    Fail-safe defaults

    When something goes wrong or is ambiguous, the system should deny by default, not permit.

    Defensive copying

    Returning or storing a copy of a mutable object rather than a live reference, so callers can't silently corrupt internal state.

    Example in practice

    A recurring exercise: an Account class that returns its internal transactions array directly lets any caller mutate the account's history from outside. Returning a defensive copy closes that hole without changing the public method signature.

    // unsafe — exposes a live reference to internal state
getTransactions() { return this.transactions; }

// safer — caller gets a copy, internal state stays protected
getTransactions() { return [...this.transactions]; }

    Topics covered

    • Input validation and untrusted data at object boundariesAny point where data enters an object from outside — a network request, a file, user input — is a trust boundary, and it's the natural place to validate that data before it's allowed to affect an object's internal state. Skipping validation at the boundary means every downstream method has to defensively re-check the same data, or risk acting on something it shouldn't trust.
    • Least privilege in class and access designLeast privilege means giving a class, a method, or a user only the access it strictly needs to do its job, and nothing more. Applied to class design, this shows up as narrow constructors, minimal public methods, and access modifiers that are actually enforced rather than left permissive out of convenience.
    • Common vulnerability classes: injection, deserialization, broken access controlInjection attacks exploit code that builds a command or query by concatenating untrusted input directly into it; insecure deserialization exploits code that reconstructs objects from untrusted data without checking what it's building; broken access control happens when a system fails to verify that a caller is actually permitted to do what it's asking. All three trace back to a boundary that trusted something it shouldn't have.
    • Secure defaults and fail-safe error handlingWhen a system encounters an error, an ambiguous state, or a missing permission, its default behaviour should be to deny or restrict access rather than quietly falling back to something permissive. Designing for the failure case first, rather than treating it as an afterthought, is what the unit means by failing safe.
    • Defensive copying and immutability as security toolsReturning a copy of a mutable object, rather than a live reference to it, prevents a caller from silently corrupting an object's internal state from outside its control. Immutability takes this further by making that kind of external mutation structurally impossible, closing off an entire category of accidental or malicious state corruption.
    • Avoiding sensitive data leakage through logs, exceptions, and error messagesException messages, stack traces, and log statements are easy to overlook as an attack surface, but they can leak internal details, credentials, or personal data if they aren't deliberately scrubbed. The unit treats error-handling paths as needing the same security scrutiny as the normal, successful path through the code.
    secure coding least privilege input validation defensive copying

    Reflection

    What stood out most was how many security issues are really design issues wearing a different label — an object that over-trusts its inputs is a maintainability problem and a security problem at the same time. The defensive-copying exercise was a small, concrete example of that overlap: the fix was one line, but the underlying lesson about not exposing mutable internals applies well beyond security.

    Unit 08

    Refactoring and Code Smells

    Unit 8 turns to the maintenance side of the codebase: recognising code smells such as long methods, large classes, feature envy, and shotgun surgery, and applying targeted refactorings to resolve them without changing external behaviour.

    The unit is explicit that refactoring means something specific: changing the internal structure of code without changing what it does externally, verified by a test suite that stays green throughout. That definition rules out "refactoring" that quietly fixes a bug or adds a feature at the same time — those are separate changes that deserve their own commit, so that if something breaks, it's obvious which kind of change caused it.

    A code smell isn't a bug — it's a symptom that points at a deeper design problem, and refactoring is the disciplined, test-covered way of treating it.

    Key concepts

    Long method / god class

    A unit of code that has grown to do too much, making it hard to read, test, or change safely.

    Feature envy

    A method that spends more time reaching into another class's data than using its own — a sign it belongs elsewhere.

    Extract Method/Class

    Pulling a cohesive chunk of logic or data out into its own named method or class.

    Technical debt

    The accumulated cost of past shortcuts — useful as a metaphor for prioritising cleanup work.

    Example in practice

    A long processOrder() method mixing validation, pricing, and persistence is split with Extract Method into three named steps, each independently testable and each readable on its own.

    // before — one long method doing three jobs
processOrder(order) {
  /* validate ... */
  /* calculate totals ... */
  /* save to database ... */
}

// after — extracted, each step named and testable
processOrder(order) {
  this.validate(order);
  const total = this.calculateTotal(order);
  this.persist(order, total);
}

    Topics covered

    • Common code smells — long method, god class, feature envy, duplicated codeThese are recognisable, recurring warning signs that a class or method has grown to take on more than it should: a method too long to hold in your head at once, a class that's become a dumping ground for unrelated logic, a method that spends more time reaching into another object's data than its own, or the same logic copy-pasted in multiple places.
    • Extract Method / Extract Class refactoringsExtract Method pulls a cohesive chunk of logic out of a larger method and gives it its own name, making the original method easier to read and the extracted piece independently testable. Extract Class does the same thing at a larger scale, pulling a group of related fields and methods out into a class of their own.
    • Replacing conditionals with polymorphismA conditional that repeatedly checks an object's type or category to decide what to do is often better expressed as a small hierarchy of classes, each of which simply knows how to behave for its own case. This mirrors the behavioural-pattern work from Unit 5, applied here specifically as a refactoring technique for cleaning up existing code.
    • Refactoring safely under test coverageA solid test suite is what turns refactoring from a risky rewrite into a safe, incremental process — each small change can be checked against the existing tests, and a broken test immediately flags that behaviour has changed when it wasn't supposed to. Without that safety net, refactoring becomes much closer to guessing.
    • Technical debt as a design and communication conceptTechnical debt is a useful metaphor for the accumulated cost of past shortcuts — code that works but wasn't built to last, waiting to be paid down later with interest in the form of slower future changes. As a communication tool, it also gives a team a shared vocabulary for prioritising cleanup work against new feature work.
    • Separating refactoring commits from behaviour-changing commitsKeeping a refactoring commit strictly separate from one that changes actual behaviour makes each commit easier to review, and makes it far easier to pinpoint the cause if something later breaks. Mixing the two together — cleaning up code while also fixing a bug — makes both changes harder to trust in isolation.
    refactoring code smells extract method technical debt

    Reflection

    Working through a "smelly" class step by step made it clear that refactoring is most effective as a sequence of small, reversible moves rather than one large rewrite. The rule about keeping refactoring commits separate from behaviour changes was simple but something I hadn't been disciplined about before — it makes code review, and any later bisecting for a bug, noticeably easier.

    Unit 09

    Object-Oriented Software Architecture

    Unit 9 zooms out from individual classes to the architecture of a whole system, covering layered architecture, package and module boundaries, and architectural styles such as MVC, hexagonal, and service-oriented approaches, all viewed through an object-oriented lens.

    The unit's working definition of architecture is "the decisions that are expensive to change later" — which database to use, how modules are allowed to depend on each other, where the boundary between business logic and infrastructure sits. It argues that good object-oriented architecture is mostly about controlling the direction dependencies point: business logic should not depend on infrastructure details like a specific database or web framework, even though at runtime it needs them.

    Architecture is design decisions that are expensive to reverse — the unit frames every architectural choice as a trade-off between flexibility now and cost later.

    Key concepts

    Layered architecture

    Organising code into layers — presentation, business logic, data — where each layer only depends on the one below it.

    Coupling & cohesion

    Cohesion measures how related the responsibilities inside a module are; coupling measures how tangled modules are with each other.

    MVC

    Splits an application into Model (data/logic), View (presentation), and Controller (coordination).

    Hexagonal architecture

    Keeps business logic at the centre, reachable only through ports, with adapters plugging in the outside world.

    Example in practice

    A hexagonal-architecture exercise defines an OrderRepository interface (a port) that the business logic depends on, with a PostgresOrderRepository adapter implementing it — so the core logic never imports anything database-specific.

    // port — defined by the business logic, owned by the core
interface OrderRepository {
  save(order: Order): void;
  findById(id: string): Order;
}

// adapter — implements the port, lives on the outside
class PostgresOrderRepository implements OrderRepository {
  save(order) { /* SQL details live here, not in core logic */ }
  findById(id) { /* ... */ }
}

    Topics covered

    • Layered architecture and separation of concernsLayered architecture organises a system into distinct layers — presentation, business logic, data access — where each layer is only allowed to depend on the layer directly below it. This keeps concerns cleanly separated: a change to how data is displayed shouldn't require touching the business rules underneath it, and vice versa.
    • Package and module boundariesDeciding what belongs inside a given package or module, and what's allowed to depend on what across those boundaries, is one of the most consequential and hardest-to-reverse decisions in a codebase. Poorly drawn boundaries tend to produce modules that are tangled together and can't be changed, tested, or deployed independently.
    • MVC and its variantsMVC splits an application into a Model that holds data and business logic, a View that handles presentation, and a Controller that coordinates between the two. Its many variants adjust exactly where responsibilities sit, but the underlying goal stays the same: keeping data, display, and coordination logic from bleeding into each other.
    • Hexagonal / ports-and-adapters architectureHexagonal architecture keeps business logic at the centre of a system, reachable only through explicitly defined ports, with adapters plugging in whatever the outside world requires — a specific database, a web framework, a message queue. This means the core logic can be tested, and even reused, entirely independently of any particular infrastructure choice.
    • Coupling and cohesion at the system levelCohesion measures how closely related the responsibilities inside a single module are, while coupling measures how entangled separate modules have become with each other. The unit's architectural goal, stated repeatedly, is high cohesion within modules paired with low coupling between them — modules that each do one clear thing and depend on each other as little as possible.
    • Controlling the direction of dependencies between layersBusiness logic should not depend directly on infrastructure details like a specific database or web framework, even though it needs those things to actually run. Controlling the direction dependencies point — infrastructure depending on abstractions defined by the business logic, rather than the other way around — is what makes a system's core logic portable and testable in isolation.
    architecture layered design hexagonal architecture MVC

    Reflection

    Seeing hexagonal architecture as "dependency inversion applied to the whole application" connected this unit back to SOLID in a way that made both easier to remember. It reframed a lot of earlier "just import the database client where you need it" habits as a shortcut that architecture-level thinking specifically warns against.

    Unit 10

    Test-Driven Development (TDD) and Behaviour-Driven Development (BDD)

    Unit 10 covers the red-green-refactor cycle of TDD and the specification-by-example style of BDD, treating tests as a design tool rather than only a verification step, and working through the Given/When/Then structure used in BDD scenarios.

    The unit distinguishes TDD's audience from BDD's: TDD tests are written by and for developers, driving the internal design of a class one small step at a time. BDD scenarios are written to be readable by non-technical stakeholders too, describing behaviour from the outside in plain language — the two are complementary rather than competing techniques, often used together at different levels of a system.

    Writing the test first forces an interface decision before an implementation one — the unit's argument is that this ordering, not the tests themselves, is what improves the design.

    Key concepts

    Red-Green-Refactor

    Write a failing test, write the minimum code to pass it, then improve the structure with tests as a safety net.

    Given/When/Then

    BDD's structure for describing behaviour: starting context, the action taken, and the expected outcome.

    Test doubles

    Mocks, stubs, and fakes stand in for real collaborators so a class can be tested in isolation.

    Testable design

    Classes that depend on injected abstractions are naturally easier to test than ones that construct their own dependencies.

    Example in practice

    A TDD exercise builds a ShoppingCart.applyDiscount() method one test at a time, starting from the simplest case (no discount) before handling percentage and fixed-amount discounts.

    // Given/When/Then, BDD-style
describe("applying a loyalty discount", () => {
  it("reduces the total by 10% for members", () => {
    // Given a cart with $100 of items and a loyalty member
    const cart = new ShoppingCart(100, { isMember: true });
    // When the discount is applied
    const total = cart.applyDiscount();
    // Then the total reflects the 10% reduction
    expect(total).toBe(90);
  });
});

    Topics covered

    • The red-green-refactor cycleThe cycle starts with a failing test (red) that describes behaviour that doesn't exist yet, followed by writing just enough code to make it pass (green), and finally improving the internal structure of that code with the test suite acting as a safety net (refactor). Repeating this cycle in small steps is what drives the design forward one decision at a time.
    • Unit tests as executable design specificationsA well-written unit test does more than verify correctness after the fact — read on its own, it documents exactly what a class is supposed to do in a given situation, in a form that stays accurate because it's checked automatically every time the suite runs. That documentation-by-test tends to age far better than comments or separate written specs.
    • BDD and the Given/When/Then structureBDD scenarios describe behaviour in plain, readable language using a Given/When/Then structure: the starting context, the action taken, and the expected outcome. Writing scenarios this way makes them understandable to non-technical stakeholders too, turning a test suite into something closer to a shared, living specification of what the system does.
    • Test doubles — mocks, stubs, and fakesMocks, stubs, and fakes are all stand-ins for a real collaborator that let a class be tested in isolation, without needing to involve a real database, network call, or other slow or unpredictable dependency. Each type of double serves a slightly different purpose — verifying interactions, returning canned data, or providing a lightweight working implementation.
    • Testable design and dependency isolationA class that accepts its dependencies from the outside, rather than constructing them internally, is naturally far easier to test, since a test can simply supply a double in place of the real dependency. This connects testing directly back to the dependency injection ideas covered later in Unit 11 — testable design and injectable design turn out to be much the same thing.
    • Where TDD and BDD fit together in one workflowTDD and BDD operate at different levels and different audiences: TDD's fine-grained tests drive the internal design of individual classes, while BDD's scenarios describe a system's behaviour from the outside in language a stakeholder can follow. Many teams use both together, with BDD scenarios describing the overall feature and TDD driving the implementation underneath it.
    TDD BDD test doubles testable design

    Reflection

    Writing a failing test before any implementation felt slower at first, but it consistently produced simpler class interfaces than designing the class first and testing it afterward. The Given/When/Then structure also turned out to be a good thinking tool even outside formal BDD — writing a scenario in plain language before touching code surfaces edge cases early.

    Unit 11

    Dependency Injection and Inversion of Control (IoC)

    Unit 11 examines how objects should acquire their dependencies. It contrasts objects that construct their own collaborators with objects that receive them from the outside, and introduces IoC containers as a mechanism for wiring large object graphs.

    Inversion of Control is presented as the broader principle — control over when and how a piece of code runs is handed to a framework or container rather than the code itself — and Dependency Injection as the specific, common case of that principle applied to constructing collaborators. The unit is careful to separate DI, a straightforward technique any class can use, from IoC containers, which are a convenience for wiring large graphs and not a requirement for doing DI at all.

    Dependency Injection is Dependency Inversion made concrete — the unit ties this back directly to the "D" in SOLID from Unit 2.

    Key concepts

    Constructor injection

    Dependencies are passed in when an object is created, making them explicit and required.

    Setter/interface injection

    Dependencies are supplied after construction, useful for optional collaborators.

    IoC container

    A framework component that wires up an object graph automatically based on declared dependencies.

    Service locator (anti-pattern)

    Hides a class's real dependencies behind a global lookup, making them hard to see or test.

    Example in practice

    An OrderService that constructs its own EmailSender internally is hard to test without sending a real email. Injecting the dependency through the constructor lets a test supply a fake instead.

    // before — hidden dependency, hard to test
class OrderService {
  private emailSender = new SmtpEmailSender();
}

// after — injected dependency, easy to substitute in tests
class OrderService {
  constructor(private emailSender: EmailSender) {}
}

// test
const service = new OrderService(new FakeEmailSender());

    Topics covered

    • Constructor, setter, and interface injectionThese are the three common ways a class can receive its dependencies from outside rather than constructing them itself: through the constructor at creation time, through a setter method after construction, or through an interface the class implements. Constructor injection is generally preferred for required dependencies, since it makes them explicit and impossible to forget.
    • Inversion of Control as a general principleInversion of Control is the broader idea of handing control over what code runs, and when, to a framework or container rather than having a piece of code call the shots itself. Dependency injection is simply the most common, concrete application of that broader principle, specifically applied to how objects get their collaborators.
    • IoC containers and object graph wiringAn IoC container is a piece of framework tooling that automatically assembles a large graph of interdependent objects, wiring each one's dependencies together based on configuration or annotations rather than manual code. It's a convenience for managing complexity at scale, not a requirement for practicing dependency injection at all.
    • Testability benefits of injected dependenciesBecause an injected dependency is supplied from outside rather than built internally, a test can simply pass in a fake or mock implementation in its place, without needing to modify the class under test at all. This is one of the most immediate, practical payoffs of dependency injection, felt the moment you try to write a test for a class that doesn't yet use it.
    • Common anti-patterns — service locators, hidden dependenciesA service locator hides a class's real dependencies behind a global lookup call, which looks convenient but makes those dependencies invisible from the class's own signature and much harder to test or reason about. Hidden dependencies of any kind undermine the main benefit dependency injection is meant to provide: visibility into what a class actually needs.
    • Distinguishing DI as a technique from IoC containers as toolingDependency injection itself is just a technique — passing collaborators in rather than constructing them internally — and it can be practiced by hand in any codebase with no framework at all. IoC containers are a separate, optional layer of tooling for automating that wiring at scale, and adopting one is not a prerequisite for getting DI's benefits.
    dependency injection inversion of control testability IoC containers

    Reflection

    Constructor injection in particular made a class's dependencies visible just from reading its signature — a small change that had an outsized effect on how easy the code was to reason about. Distinguishing DI from IoC containers was also useful: it clarified that adopting dependency injection doesn't require adopting a heavyweight framework at the same time.

    Unit 12

    Recent Developments and Review

    The final unit looks at recent developments touching object-oriented design — the influence of functional programming ideas on OO languages, the growing use of composition over inheritance in modern codebases, and how OO principles interact with microservice and distributed architectures. It closes with a review across all eleven preceding units.

    Rather than presenting these as a break from what came before, the unit treats them as the same principles under new pressures. Functional-style immutability, for instance, is the same defence against shared mutable state introduced back in Unit 6 on concurrency. Microservices push module boundaries — Unit 9's territory — out to the network, where the cost of a badly drawn boundary is a network call instead of a misplaced import.

    The throughline across the course is that every technique studied — SOLID, patterns, testing, architecture — is a different lens on the same underlying goal: software that can change without breaking.

    Key concepts

    Functional influence

    Immutability, pure functions, and first-class functions increasingly show up inside mainstream OO languages.

    Composition over inheritance

    Modern codebases favour assembling behaviour from small collaborators over deep class hierarchies.

    Distributed OO design

    Microservices turn module boundaries into network boundaries, raising the cost of getting them wrong.

    Course throughline

    Every unit, in different language, argues for small, explicit, loosely coupled responsibilities.

    Example in practice

    A closing exercise re-examines a Unit 1 inheritance hierarchy and rewrites it using composition, showing the same behaviour assembled from smaller, independently testable collaborators instead of a rigid class tree.

    // inheritance — rigid, one hierarchy per axis of variation
class FlyingRobot extends Robot { /* ... */ }

// composition — behaviours assembled, mixed freely
class Robot {
  constructor(private movement: MovementBehaviour) {}
  move() { this.movement.move(); }
}
const robot = new Robot(new FlyingBehaviour());

    Topics covered

    • Functional influences on modern object-oriented languagesIdeas from functional programming — immutability, pure functions with no side effects, first-class functions passed around as values — increasingly show up inside mainstream object-oriented languages rather than staying confined to purely functional ones. These aren't a rejection of OOP so much as additional tools that address some of the same problems, like shared mutable state, from a different angle.
    • Composition over inheritance in current practiceModern codebases increasingly favour assembling an object's behaviour out of several small, focused collaborators rather than building deep, rigid inheritance hierarchies. This isn't a rejection of inheritance so much as a shift in the default — reach for composition first, and treat inheritance as a deliberate exception rather than the starting point.
    • OO design in distributed and microservice systemsMicroservices take the module boundaries discussed back in Unit 9 and push them out across the network, so that a badly drawn boundary now costs a network call and a versioning headache instead of just a misplaced import. The underlying object-oriented design questions stay the same; the stakes of getting them wrong simply get higher.
    • Course review — connecting Units 1 through 11Looking back across the course, each unit builds directly on the ones before it: SOLID formalises the encapsulation ideas from Unit 1, patterns are concrete applications of SOLID, architecture applies those same ideas at a system level, and testing and dependency injection make all of it verifiable and swappable in practice.
    • Where object-oriented design is heading nextCurrent trends point toward object-oriented design absorbing more functional influence, taking module boundaries more seriously as systems become more distributed, and continuing to lean on composition and explicit dependencies over rigid, implicit structure. The core goal running through all of it stays unchanged: software that can be changed safely.
    • Revisiting Unit 1's inheritance example through a composition lensTaking the original inheritance-based example from Unit 1 and rebuilding it with composition instead makes the course's overall argument concrete — the same problem, solved with smaller, independently swappable collaborators instead of a fixed class hierarchy, using everything covered in between.

    Looking back, the course reads as one continuous argument, starting from encapsulation in Unit 1 and ending with distributed systems in Unit 12, for keeping responsibilities small, explicit, and loosely coupled. Rewriting the Unit 1 inheritance example with composition was a satisfying way to close the loop — the same problem, solved with everything picked up along the way.
